Below is a **precise implementation roadmap in English** based on the latest deep audit of the Hilbras AI SDK. The goal is to stabilize the current architecture rather than replace it, and to make **v1.0 a reliability/stability release instead of another feature-heavy release**.

# Hilbras AI SDK — Production Hardening & v1.0 Roadmap

## 1. Main Objective

The current SDK already has a broad and mature feature set. The next stage should **not focus on adding more features**.

The primary objective is:

> **Turn the existing feature-rich SDK into a production-grade, reliable, secure, correctly packaged, and API-stable SDK suitable for v1.0.**

The main areas requiring work are:

1. Transport correctness
2. Streaming lifecycle
3. Request coalescing
4. Connection/concurrency semantics
5. Resource cleanup
6. Reliability concurrency
7. Package/workspace consistency
8. npm package verification
9. CI coverage
10. Public API stability
11. Documentation accuracy
12. Final v1.0 release validation

# Phase 1 — Fix FetchTransport

This is the **highest-priority phase**.

## Problem

The current implementation describes itself as connection pooling, but the actual behavior is closer to:

> **per-origin request concurrency limiting**

It relies on `fetch()` for underlying connection reuse instead of owning a real HTTP connection pool.

Therefore, the implementation and terminology need to be aligned.

---

## 1.1 Rename the internal concept

Determine whether the implementation should remain a true connection pool or become an explicit:

```text
OriginConcurrencyLimiter
```

If the underlying HTTP implementation is responsible for TCP/TLS connection reuse, do not falsely claim that the SDK owns the connection pool.

### Preferred architecture

```text
HilbrasClient
      │
      ▼
FetchTransport
      │
      ├── OriginConcurrencyLimiter
      │
      ├── Request Lifecycle
      │
      ├── Abort Handling
      │
      └── Fetch
```

The terminology must accurately describe what the implementation actually controls.

---

# Phase 2 — Fix Resource Acquisition and Release

## Problem

The current transport can release an origin slot from multiple locations.

There is a possible flow where:

```text
requestFn()
   ↓
finally
   ↓
_release(origin)
```

and then:

```text
catch
   ↓
_release(origin)
```

This can result in a **double release**.

---

## Required change

Create one authoritative ownership model.

For every acquired slot:

```text
acquire()
   ↓
exactly one release()
```

Never allow multiple layers to independently release the same resource.

### Recommended pattern

```text
const lease = await acquire(origin)

try {
    return await executeRequest()
} finally {
    lease.release()
}
```

The release operation should ideally be idempotent:

```text
lease.release()
lease.release()
```

must never corrupt pool state.

### Tests

Add tests for:

* successful request
* fetch failure
* timeout
* abort
* HTTP error
* streaming response
* synchronous failure
* asynchronous failure
* repeated release

# Phase 3 — Fix Streaming Lifecycle

This is one of the most important correctness issues.

## Current problem

The transport currently treats:

```text
fetch() resolves
```

as:

```text
connection/request finished
```

But for streaming:

```text
fetch()
   ↓
Response returned
   ↓
ReadableStream still active
```

The network operation is **not actually finished**.

Therefore, releasing the origin slot immediately after `fetch()` resolves means:

```text
maxConnectionsPerOrigin
```

does not actually limit active streaming connections.

---

## Required architecture

For non-streaming:

```text
acquire
  ↓
fetch
  ↓
consume/complete response
  ↓
release
```

For streaming:

```text
acquire
  ↓
fetch
  ↓
return wrapped stream
  ↓
stream consumed / cancelled / errored
  ↓
release
```

The resource lease must remain active until the stream reaches a terminal state.

Terminal states:

```text
complete
error
cancel
abort
```

Each must release exactly once.

---

# Phase 4 — Add Explicit Transport Lifecycle

## Problem

The transport starts an interval:

```text
setInterval(...)
```

for idle cleanup.

However, the lifecycle does not clearly expose a matching:

```text
clearInterval(...)
```

operation.

This creates a resource-lifecycle problem.

---

## Required API

Introduce:

```text
transport.dispose()
```

or equivalent.

It must:

1. Stop cleanup timers
2. Abort active requests if appropriate
3. Clear pool state
4. Clear pending requests
5. Release internal resources
6. Become idempotent

Example lifecycle:

```text
new Transport()
      ↓
running
      ↓
dispose()
      ↓
disposed
```

After disposal:

```text
new request → rejected clearly
```

No silent undefined behavior.

# Phase 5 — Redesign Request Coalescing

The current request coalescing design requires significant hardening.

## Problem 1 — Security

The key currently resembles:

```text
method + url + body
```

but does not include authentication-sensitive headers.

Therefore:

```text
Request A
Authorization: API_KEY_A

Request B
Authorization: API_KEY_B
```

could theoretically resolve against the same coalesced request.

That is unacceptable.

---

## Required solution

At minimum, coalescing identity must account for all request properties that can change the response.

However, **never blindly include raw secrets in the key**.

Do not create keys such as:

```text
Authorization: sk-secret...
```

Instead use a safe request identity mechanism.

For example:

```text
method
URL
body hash
relevant headers hash
credential scope
```

with secrets represented by a cryptographic hash or isolated credential identity.

---

# Phase 6 — Disable Streaming Coalescing Until Safe

This should be an explicit rule.

Do **not** coalesce:

```text
stream: true
```

requests using the current single-`Response` architecture.

A `Response`/`ReadableStream` cannot safely be consumed by multiple independent callers.

Therefore:

```text
if streaming:
    bypass coalescing
```

until a proper multicast/subscriber architecture exists.

---

## Future architecture

If streaming coalescing is ever implemented:

```text
                 ┌── Consumer A
                 │
Network Stream ──┼── Consumer B
                 │
                 └── Consumer C
```

The SDK would need:

* subscriber management
* buffering strategy
* backpressure handling
* cancellation semantics
* subscriber failure isolation
* stream termination handling

This should **not** be rushed into v1.0.

---

# Phase 7 — Define Correct Coalescing Semantics

Coalescing should only happen when requests are truly equivalent.

Define a deterministic identity function:

```text
RequestIdentity
```

Possible components:

```text
HTTP method
normalized URL
request body hash
relevant headers
credential scope
request options affecting response
```

Document exactly what makes two requests equivalent.

---

## Required tests

Test:

```text
same request → coalesced

different URL → not coalesced

different body → not coalesced

different authorization scope → not coalesced

different relevant headers → not coalesced

streaming → not coalesced

failed request → pending state cleaned

cancelled request → pending state cleaned
```

# Phase 8 — Reliability / Circuit Breaker Concurrency Audit

The circuit breaker implementation should be reviewed specifically for concurrent calls.

## Problem

The existence of:

```text
halfOpenMaxCalls
_halfOpenCalls
```

does not automatically guarantee atomic reservation.

A concurrent sequence could theoretically be:

```text
Call A → isAvailable() → true
Call B → isAvailable() → true
Call C → isAvailable() → true
```

before the counter is updated correctly.

---

## Required design

Separate:

```text
availability check
```

from:

```text
probe reservation
```

Use an explicit concept such as:

```text
acquireProbe()
```

The operation should atomically enforce:

```text
active half-open probes <= halfOpenMaxCalls
```

---

## Required concurrency tests

Run:

```text
1 concurrent call
10 concurrent calls
100 concurrent calls
1000 concurrent calls
```

and verify:

```text
half-open probe limit never exceeded
```

Also test:

* success
* failure
* timeout
* cancellation
* simultaneous recovery

## The key principle

**Do not turn v1.0 into “more features.”**

The SDK already has enough functionality to justify a serious stable release. The critical work now is making every existing feature **correct under concurrency, streaming, failure, cancellation, packaging, and long-running production workloads**.

The single highest-risk area identified in the audit is currently **`FetchTransport`**, followed by **request coalescing** and **multi-package release integrity**. Those should be resolved before the project spends significant effort on additional features.
