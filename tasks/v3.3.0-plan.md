# Implementation Plan: v3.3.0 Configuration Architecture

> **Historical.** The v3.3.0 plan. Shipped. See `tasks/v3.5.0-todo.md`.

## Scope

Implement the specification in [`SPEC-v3.3.0-config.md`](../SPEC-v3.3.0-config.md)
as an additive, backward-compatible release. Do not remove providers, change
provider adapters, or introduce runtime dependencies.

## Dependency order

```text
config-schema
      ↓
config-sources
      ↓
config-resolver
      ↓
client-integration
      ↓
compat-docs
      ↓
release-gate
```

## Phase 0 — Baseline and contract tests

### Task 0.1: Freeze current configuration behavior

- Add characterization tests for `loadConfig`, `createConfig`, and
  `validateConfig`.
- Record current precedence, environment variable names, adapter inference, and
  file-error behavior.
- Do not change runtime behavior in this task.

**Acceptance:** tests pass against the v3.2.0 baseline and document which legacy
behaviors must remain compatible.

**Verify:** `npx vitest run tests/config.test.ts tests/config/`

**Files:** new `tests/config/legacy-compat.test.ts`; existing config tests.

### Task 0.2: Add configuration risk tests

Cover:

- malformed environment numbers/booleans;
- unknown keys;
- secret leakage in diagnostics;
- caller mutation after resolution;
- Node-only imports in universal modules.

**Acceptance:** tests describe the desired strict resolver behavior and remain
red until each corresponding implementation task lands.

**Verify:** focused Vitest runs.

## Phase 1 — Schema and diagnostics

### Task 1.1: Define configuration contracts

Create `src/config/config-schema.ts` with:

- `ConfigSourceKind`;
- `ConfigDiagnostic`;
- `ConfigSource` and `ConfigSourceResult`;
- strict field parsers/validators;
- schema-owned defaults.

Keep `SDKConfig` and `DEFAULT_CONFIG` compatible while moving their canonical
ownership into the new schema module.

**Acceptance:** contracts are typed, documented, and free of client/provider
implementation imports.

**Verify:** `npx tsc --noEmit` and contract tests.

### Task 1.2: Add redacted resolved configuration types

Create `src/config/resolved-config.ts` with:

- `ResolvedSDKConfig`;
- `SafeSDKConfig`;
- redacted snapshot generation;
- winning-source metadata;
- immutable defensive copies.

**Acceptance:** no raw authentication value can appear in a safe snapshot or
diagnostic string.

**Verify:** secret-redaction tests.

## Phase 2 — Source adapters

### Task 2.1: Defaults source

Create `src/config/sources/defaults.ts` and re-export the existing defaults for
compatibility.

**Acceptance:** returned defaults cannot be mutated through the source result.

### Task 2.2: Environment source

Create `src/config/sources/environment.ts` with an injected `env` object and
strict parsers for:

- provider/default fields;
- finite numeric values;
- documented booleans;
- log levels;
- provider URL/key pairs.

Preserve `HILBRAS_PROVIDER_*` compatibility and SSRF validation.

**Acceptance:** malformed values produce typed diagnostics/errors, never `NaN`
or silent `false` values.

### Task 2.3: File source

Create `src/config/sources/file.ts` with an injected `readFile` function. Keep
Node file reading in the legacy compatibility facade only.

**Acceptance:** the universal source has no `node:fs` import; missing and
malformed files follow explicit policy.

### Task 2.4: Runtime source

Create `src/config/sources/runtime.ts` with defensive copying and atomic array
replacement semantics.

**Acceptance:** mutating the caller's override object after resolution cannot
change the resolved configuration.

## Phase 3 — Resolver

### Task 3.1: Implement deterministic merge and precedence

Create `src/config/config-resolver.ts` with:

- source ordering;
- schema-aware merge;
- arrays replaced atomically;
- winning-source tracking;
- unknown-key diagnostics;
- strict-mode aggregation.

**Acceptance:** precedence is deterministic for every field and covered by
property-style tests.

### Task 3.2: Implement validation aggregation

Validate:

- numeric ranges and integer requirements;
- booleans and log levels;
- provider names, adapters, authentication, models, and URLs;
- duplicate providers;
- allowed/denied tool overlap.

**Acceptance:** all errors identify the source and config path without exposing
secrets.

### Task 3.3: Preserve the legacy facade

Refactor `src/config/config.ts` so it delegates to the new resolver while
retaining:

- `loadConfig(options)`;
- `createConfig(overrides)`;
- `validateConfig(config)`.

The facade must remain Node-compatible and document its legacy permissive
behavior.

## Phase 4 — Client integration

### Task 4.1: Resolve once in `HilbrasClient`

Add an additive canonical config input while keeping `sdkConfig` supported.
Resolve during construction and map policy, budget, and providers once.

**Acceptance:** request execution never reads environment variables or files.

### Task 4.2: Remove duplicate mapping logic

Move `_policyFromSDK` and `_budgetFromSDK` behavior behind one internal
resolved-config adapter. Preserve explicit `policy`/`budget` precedence.

**Acceptance:** client tests pass without duplicated precedence logic.

### Task 4.3: Add configuration diagnostics

Expose safe configuration diagnostics through the existing diagnostics/observability
surface without logging secrets.

## Phase 5 — Documentation and migration

### Task 5.1: Write configuration documentation

Create `docs/configuration.md` covering sources, precedence, validation,
secret handling, browser boundaries, and examples.

### Task 5.2: Write migration guide

Create `docs/migration-from-v3.2.md` with old/new examples and explicit
compatibility notes.

### Task 5.3: Update active docs and examples

Update README, API reference, examples, and migration references without
rewriting historical changelog entries.

### Task 6.3: Release

- Update `package.json`, `package-lock.json`, README, CHANGELOG, docs, and audit.

- Verify the published package in a clean project.
- Do not lower coverage thresholds.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Configuration precedence changes | Characterization tests and compatibility facade |
| Secret leakage | Safe snapshot, redaction tests, no raw diagnostics |
| Browser bundle regression | Injected file reader and import-boundary tests |
| Prototype pollution or unsafe merge | Schema-owned keys and explicit merge |
| Client behavior drift | One-time resolution plus integration tests |
| Scope creep into providers | Explicitly exclude provider/adapter changes |
| Coverage gate remains below target | Add focused config tests; never lower thresholds |
